# observer-agent-lab

我在 Parable 项目里负责「观察者 Agent」这条线的个人产出存档。

本地一份，GitHub 一份，双端保存。

---

## 这是什么

Parable 是一个访谈训练系统：三个 Agent 各干一件事——采访者提问、受访者按人物卡作答、观察者给采访者的提问质量打分。我负责观察者，顺手把三个 Agent 串成了一个能自己跑的 demo。

这个仓库存的是**我自己写的那部分**：评分标准提案、编排器脚本、QA、演示说明、终端小抄，以及两场实测记录。

它不是一个能独立运行的完整项目。三个 Agent 的程序包属于团队仓库，不在这里。

**要运行 demo，把 `tools/orchestrator/` 整个目录复制回团队仓库的根目录下**，然后：

```bash
node tools/orchestrator/run.mjs --rounds 8 --mode assisted
```

它靠相对路径去找 `Service_agents/` 下那三个包，离开团队仓库就找不到人。

## 现在的进度

**状态：可演示。** 能跑通一场完整的自主访谈，但还没到能交付。

已经做到的：

- 三个 Agent 串成循环，自己推进八轮访谈
- 观察者逐轮出分（五项加权）、出追问方向、判断这一轮有没有拿到新东西
- 隔离自检每次通过：采访者的输入里查不到人物卡内容
- 埋点召回率能算：人物卡埋 10 条关键信息，跑完数挖出几条

还差得远的：

- 召回率 4/10，挖到的信息还是太少
- 人物卡是临时草案，组长没确认
- 评分口径有两版没合并（上游四维 vs 我的五项）
- 报告是工程师视角的 JSON，不是律师读得懂的一页纸

## 实测数据

| 场次 | 轮数 | 过程均分 | 召回 | 隔离自检 |
|---|---|---|---|---|
| assisted-final8 | 8 | 4.45 | 4 / 10 | 通过 |
| assisted-audit3 | 4 | 4.56 | 3 / 10 | 通过 |

之前跑过六场对照，出现过一个反直觉的结果：过程分更高的那一场，挖到的关键信息反而更少。这也是我把评分标准改成三层、不合成总分的原因。
