## 00 三十秒版本

**我们要做的是一套能从访谈中稳定提取「可验证、可迁移的价值判断与决策规则」的系统。**

最终不以对话流不流畅作为成功标准，而是看一件事：**通过访谈获得的认知，能不能帮模型预测这个人在没见过的情境里会怎么选。**

现在的状态：三个 Agent 已经能各自跑通，缺一个把它们串成一场完整访谈的编排器。

## 01 我们在做什么

### Q1 这个项目到底要解决什么问题

**解决「访谈质量无法衡量，也无法积累」这件事。**

律师做完一场访谈，拿到了录音和文字，但说不清这场问得好不好、下一句该怎么改、换个人来问会不会更好。这些判断目前只能靠带教律师的主观感觉。

三个 Agent 合起来，是让「访谈质量」从一种感觉变成一个可以打分、可以比较、可以留存的数。

### Q2 谁在用这套东西

| 用户 | 怎么用 |
|---|---|
| 项目团队（当前主要用户） | 在工作台跑模拟访谈，评估提问质量，迭代三个 Agent |
| 律师 | 主持真实访谈，提取创始人的价值偏好与判断依据 |
| 家族创始人 | 作为最终受访者，形成认知资产，保留人工修改权 |
| 家族后代 / 治理参与者（远期） | 消费认知报告与制度解释 |

### Q3 律所为什么需要这个

**他们买的是一把尺子，不是三个 Agent。**

同一套标准算出分，换人、换案、换时间都能比。记录攒下来，律所自己能看新人提问水平的走势，也能看全所的共同毛病。这是「数据留存」的商业价值所在。

三个角色只是让这把尺子得以成立的手段。

### Q4 有人说「这像后端逻辑，不对用户暴露」

**这句话对一半，需要拆成两层看。**

内部结构确实不暴露。三个 Agent、人物卡、评分细则，用户都看不见，也应该看不见。

结论必须暴露。这一场几分、哪三句问得不好、原话是什么、改成什么问法。不暴露这个，付钱的人拿到的是黑箱。

用户碰到的动作很少，具体是哪几个，取决于走哪种模式，见 Q4b。前台轻、后台重，这是设计选择。前台如果也重，访谈员就不愿意用了。

### Q4b 到底是 Agent 自主访谈，还是人访谈完再丢记录进来

**两种都是，是两个不同的模式，不是同一个产品的两种说法。**

|  | 模拟访谈（sandbox） | 真实访谈（real） |
|---|---|---|
| 谁在场上 | 三个 Agent 自己跑 | 律师 + 家族创始人 |
| 人干什么 | 配人物卡、按开始、看报告 | 主持访谈 |
| 采访者是谁 | interviewer Agent | 真人律师 |
| 观察者评谁 | 评 interviewer Agent | 评律师 |
| 什么时候出结果 | 每轮可快评，收尾出总评 | 访谈结束后统一评 |
| 拿来干什么 | 迭代采访者的提问策略、跑对照实验 | 提炼认知资产、带教新人 |

对应 project-brief 里的流程：模拟访谈是流程 1，评估比对是流程 2，真实访谈是 L1+ 的流程 3。

**两个模式的差别不只是谁在说话，是产出物的用途不同。** 模拟访谈里，观察者的反馈用来改采访者 Agent 本身，改完可以固化成 prompt 或策略。真实访谈里，观察者的反馈用来改那个律师，只能一场一场攒。

**实时反馈只做在模拟访谈里。** 真实访谈里给律师提词，形式只能是手机或耳机，律师低头看屏幕，一场深谈的信任感就散了，尤其对方是年长的创始人。这条路产品上很窄。

## 02 三个角色

### Q5 三个 Agent 是独立应用，还是一个父 Agent 带三个子 Agent

**是三个独立副本，外加一个还没建的编排器。**

部署这一层已经是事实：`Service_agents/{interviewer,observer,respondent}` 是三份完整副本，各有各的 `package.json`，各自 `pnpm install`、各自 `pnpm dsh` 启动，互不引用代码，也不读对方内部状态。

不建议做成父带子。三套人格跑在同一个进程里，采访者迟早能读到人物卡，答案就泄漏了，访谈失去意义。边界靠代码自觉守不住，靠进程分布才守得住。

### Q6 他们会出现在同一时刻吗

**说话严格交替，观察全程并行。**

同一时刻只有一个人拿着话筒。采访者问完停下，受访者答完停下。真实访谈里有人抢话，那恰恰是观察者要扣分的项。

观察者全程在场但不发声，像坐在单面玻璃后面的督导。它和对话是并行的，不是轮到它才启动。

今天的现实是只能分着用。编排器还没做，没人递话筒，所以只能一次启动一个进程、单独对话。这是现状的限制。

### Q7 为什么需要受访者 Agent，真人回答不行吗

**因为这套系统测的是采访者，被问的人必须固定不变。**

两个新人各跑十场。如果受访者是真人，A 碰上三个健谈的，B 碰上三个闷的，最后 A 分高。这个分说明 A 运气好，说明不了 A 问得好。

换成受访者 Agent，两个人对着同一张人物卡各跑十场，分数的差别只可能来自提问方式。这才叫可比较。

真人有另外三件事做不到：被问到第十遍同一个问题回答就变味；会不自觉地顺着采访者说话，甚至替对方补全；需要排期、付费、转录。受访者 Agent 三条约束（只按人物卡作答、证据不足要来源、不配合诱导）就是用来压住这些污染的。

### Q8 受访者只是个配角吗

**它是配角，却是不能将就的配角。**

它不是一个数据集，它是产数据的那一半。人物卡是剧本，受访者是照着剧本演的陪练，跑完落盘的那些记录才是数据集。

它演得不像，顺着采访者编故事、不追问来源、被诱导就跟着走，采访者会拿到虚高的分数。看起来问得很好，实际是对方在配合你。这种分数拿去训练，等于用假数据喂它。

### Q9 所以最重要的就是采访者

**主干是对的，补两处会更准。**

观察者不只是监督。它还给「这句该怎么问」的改写，具体到能照着说出口，更像带教的督导。它还有第二重身份：产出的分数和建议是这个系统最终交付给人看的东西，是产品的出口。

这套结构在医学教育里跑了几十年，叫**标准化病人**。采访者是考生，受访者是标准病人，观察者是阅卷兼带教，人物卡是病例脚本，编排器是考场。

## 03 观察者（当前由牛畅负责）

### Q10 观察者评的是谁

**评采访者的提问表现，不评受访者这个人。**

样例里第一轮受访者只回「我不太确定该怎么说」，这不是受访者的问题，是提问方式的问题。板子要打在采访者身上。

边界写死在 project-brief 的业务不变量里：观察者只能读 `Transcript` 和 `PersonaCard`，不能指挥受访者改答案。

### Q11 观察者的输出是什么

**四项：分数、观察、改写建议、一句话画像。**

分数是多项加权。观察要落到具体哪一句、原话是什么。改写建议要具体到能照着说出口。画像一句话总结采访者的表现。

它不重新讲一遍访谈内容，也不对受访者这个人下任何判断。

样例 `Service_agents/observer/tools/samples/transcript-01.md` 跑出 2.70 / 5，缺数据的项明写「无法判断」。

### Q12 什么时候评，访谈结束后还是进行中

**默认收尾评，实时只做安全阀，不做全程导航。**

收尾评：访谈结束给一次总分、主要毛病、可照抄的改写。这条路现在就能跑，不依赖编排器。

安全阀：只在三条硬线上介入，给受访者贴标签、诱导式提问、抢话。这三条破了，下游数据直接作废，留着没有意义。其余时候观察者不吭声。

全程导航排在编排器之后。真要做，也必须分开跑两遍，一份有介入、一份无介入，才比得出来。

### Q13 为什么不做实时全程导航

**因为观察者一旦在访谈中出声，它就从测量工具变成了干预变量。**

它提示了，采访者照着改了，最后这个高分算谁的。分和建议混在一起，就再也没法用它衡量采访者的真实水平。

还有一层：实时导航能把这一场访谈问得不错，拉不上去这个人本身的能力。前者是交付，后者是训练，两件事在同一个系统里会互相挤。

工程上也不成立。实时要求流式接口、每轮一次调用、编排器先存在，这三项今天是零。收尾评只要一次批调用。

### Q14 评分口径现在有两版，要不要对齐

**要对齐，这是目前最该处理的一处不一致。**

`design-questions.md` 里 L1 写的是四个维度：诱导性、冒犯程度、相关性、重复程度。

观察者当前实现用的是五项加权：不打断 0.30、倾听与承接 0.25、问题开放性 0.20、节奏与尊重 0.15、洞察深度 0.10。

两套能共存，因为测的层次不同：前者是质量问题清单，后者是访谈技巧评分表。但报告里必须说清哪部分是哪个口径，否则分数拿到律所面前站不住。

## 04 工程现状

### Q15 现在能跑什么

**三个 Agent 各自单跑，观察者可以对一段完整记录出分。**

`pnpm dsh` 能起对话，观察者的 `tools/observer-console.mjs` 能对单段访谈出五项加权评分。

串不成一场完整访谈。没有人管顺序，也没有人维护「第几轮、说了什么、该谁说话」这个状态。

### Q16 编排器为什么还没有

**卡在两项前置没定。**

传输形态：HTTP、进程调用还是文件交换。接口字段：`next / respond / analyze` 的输入输出结构。

这两条不定，编排器写出来必然返工。project-brief 里有 L0 契约草案，标注「待评审后以唯一登记入口为准」。

### Q17 我能改哪里

**只改组装层，不改上游 core。**

组装层是 `packages/bundle/{headless,web-app,acp-app,sdk-app}/cordis.patch.yml` 里的 `personaPrefix`，以及策略插件、评分插件。

需要改上游时，先提出理由与影响面，等团队确认。这是一票否决项。

### Q18 环境怎么配，提交前要注意什么

Node 24（本机 24.22.2），pnpm 必须 11.28.5（仓库 lockfile 锁死）。GitHub 只能走 SSH，HTTPS 不通。

提交前先跑 `git checkout -- Service_agents/*/pnpm-lock.yaml`。`pnpm install` 和 `pnpm dsh` 都会顺手改掉三个 lockfile，不还原的话 PR 里会混进几百行无关 diff。

密钥写进 `Service_agents/*/.env`（权限 600，已被 gitignore 忽略），不要提交。

### Q19 工作台是真的吗

**是纯前端 mock。**

`apps/workbench/cognitive-worker-v02.html` 自述不跑服务器、不执行导入的代码。里面预留的 `next / respond / analyze` 只有名字，当前返回 `heuristic_mock` 的假数据。

记录落盘目录 `apps/workbench/records/` 已经留好，JSON 加 Markdown 各一份，还没接上。

## 06 新人第一天做三件事

**一、跑通。** 按 `.trae/rules/env-and-workflow.md` 配环境，三个包 `pnpm install`，跑一次 `pnpm dsh`。

**二、读三份。** `docs/project-brief.md`（对象与不变量）、`docs/design-questions.md`（L1/L2 目标）、本文。

**三、只动组装层。** 改人格改 `cordis.patch.yml` 的 `personaPrefix`，提交前还原 lockfile。

有不确定的，先在群里问。这个项目现在最大的风险不是写错代码，是三个人各自想象出三套不同的系统。
