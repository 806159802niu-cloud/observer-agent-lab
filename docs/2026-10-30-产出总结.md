## 进展一：三 Agent 自主访谈跑通了

以前缺一个喊场的人，三个 Agent 只能一次启动一个。现在这个循环转起来了。

**产出**：`tools/orchestrator/run.mjs`

```bash
node tools/orchestrator/run.mjs --rounds 6 --mode assisted
```

一次调用跑完一整场：采访者提问 → 受访者按人物卡作答 → 观察者出分与追问方向 → 下一轮。
非工程同学可以双击 `tools/orchestrator/跑一场访谈.command`。

**已经具备的能力**

| 能力 | 说明 |
|---|---|
| assisted / baseline 对照 | 观察者提示回流与否，用来做对照实验 |
| 埋点召回统计 | 人物卡埋 10 条关键信息，跑完数挖出几条 |
| 隔离自检 | 每场检查送进采访者的输入里有没有人物卡内容 |
| 停止条件 | 观察者每轮判断有没有拿到新判断依据，连续两轮没有就收尾 |
| 落盘 | JSON 加 Markdown 各一份，原子写入 |

**实测数据**（`apps/workbench/records/`，28 场）

| 模式 | 场数 | 过程质量均分 | 埋点召回均值 | 隔离自检 |
|---|---|---|---|---|
| assisted（提示回流） | 13 | 4.03 | 2.38 / 10 | 全部通过 |
| baseline（不回流） | 3 | 3.97 | 3.00 / 10 | 全部通过 |

单场最高召回 4 / 10，出现在 8 轮那场。

## 进展二：探明了调用接口，编排器从「没地方挂」变成「能写」

这件事是进展一的前提。在此之前，「编排器」只是个设想，因为不知道怎么在程序里调起一个 Agent。

**接口**

```bash
cd Service_agents/<agent>
node --import tsx/esm apps/cli/src/bin.ts --profile headless --session-id <id> --json "<任务>"
```

三个踩过的坑，都已经写进 `.trae/rules/env-and-workflow.md`：

1. **首次调用不能带 `--session-id`**，带了报 does not exist。先不带跑一次，从输出第一行 `{"type":"session",...}` 里取 id。
2. **结果在最后一行**，形如 `{"type":"final","text":"..."}`。stdout 混着进度条和警告，程序要只取 `{` 开头的行。
3. **绕过 pnpm 直接调 CLI**，每次省 7 秒依赖检查。整场 6 轮 18 次调用，省下两分钟。

**一条信息边界**：观察者不能看人物卡。它一旦看到埋了哪几条关键信息，提示就会直接指向没挖出来的那几条，等于把考题答案递给考生。所以提示只能来自「受访者已经说出口、但没展开的线索」。

## 进展三：评分标准 v2 提案，以及一个反直觉的发现

这是今天真正属于自己的判断，不是执行别人的任务。

**先挖出六处历史定义，发现它们分成两派**

| | 出处 | 在问什么 |
|---|---|---|
| 纸面 | project-brief 流程 2 | 覆盖点、矛盾点、缺失点、重复提问 |
| 纸面 | project-brief 对象表 | 问题质量、一致性、重复提问、诱导检测 |
| 纸面 | project-brief API 契约 | `{ coverage, contradictions, repeats, score }` |
| 纸面 | design-questions 观察者 L2 | 获得了多少有效信息、遗漏什么 |
| 过程 | design-questions 观察者 L1 | 诱导性、冒犯程度、相关性、重复程度 |
| 实现 | rubric.json 五项加权 | 不打断 .30 / 倾听承接 .25 / 问题开放性 .20 / 节奏尊重 .15 / 洞察深度 .10 |

**核心偏移：纸面要的是结果，实现测的是过程。**

**提案**：三层分开，不合成总分。

- **L1 过程质量**：现有五项保留，回答「问得好不好」
- **L2 信息获取**：覆盖度、缺失点、矛盾点、重复，回答「挖到了什么」
- **L3 可验证性**：挖到的判断依据能不能复述成规则、能不能预测未见情境，回答「挖到的能不能用」

**支撑这个提案的，是跑出来的数据**

assisted 组过程分更高（4.03 对 3.97），召回反而更低（2.38 对 3.00）。样本不大，但方向明确：
**只用一个总分，会得出「有提示的那场更好」的结论，而它其实挖到的更少。**

这是我今天拿得出手的硬证据，不是纸面推导。

> 文档：`docs/观察者评分标准-v2提案.md`

## 进展四：观察者从「只有人格」变成「能出结构化评分」

接手时它只有一段人格文字。现在它有三条可用的路径。

**三种用法**

| 用法 | 入口 |
|---|---|
| 网页 | `pnpm dsh web`，在浏览器里对话 |
| 终端 | `tools/observer-console.mjs`，连续对话，支持 `/eval <文件>` |
| 单次评估 | 脚本内嵌，编排器调用 |

**评分口径落成了配置**：`Service_agents/observer/rubric.json`，五项各带 `unjudgeable_when`（什么情况下判为无法判断）。权重不再散落在代码里。

**输出是稳定 JSON**：`items` / `weighted_total` / `coverage` / `profile` / `suggestions`。缺数据的项记 `score: null` 并写明缺什么，不当 0 分，加权时排除并重新归一化。

**实时输出分两层**，防止自证污染：

- `hint` 回流给采访者：只给问题类型与追问方向，**不给可以照抄的问句**
- `eval` 只进记录：完整评分与改写建议，事后复盘用

## 下一步：拉召回

观察者在第 6 轮自己诊断出过一个真问题：

> 追问停留在「做法、代价」这类抽象概念层，受访者召回失败。应改成从具体个案、个案回忆重新问，再回推标准。

这条值得沉淀进采访者的人格或提示规则：**追问必须落到具体的一件事、一个时间、一个人。**

改完重跑三场，看召回有没有从 2 往上走。变了，说明找到杠杆；没变，说明瓶颈不在提问方式，得往别处找。
