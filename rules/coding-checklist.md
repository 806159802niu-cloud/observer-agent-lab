# 编码检查清单（八条）

**用法**：写新代码、改旧代码、评审别人的 PR 时，逐条过一遍。命中哪条就当场改掉，不要只在回复里罗列问题。

---

## 1. 长得一样的值写反，能不能被发现

问一句：「这两个值类型相同、含义不同，写反了，编译器或运行时能报错吗？」报不出来，就少了一层类型。

**要拦的写法**
- 同一个 `string` 既当访谈 ID 又当说话人名字
- 同一个 `number` 既当 round 序号又当评分
- 函数参数连续三个 `string`，调用时靠位置记忆

**本项目落点**：`round` 序号、`utterance` 序号、访谈 ID 三者都是数字或字符串，写反不会报错。用带名字的类型包一层，或在 TypeScript 里用 branded type。

---

## 2. 枚举要有名字，不许散在字符串里

**要拦的写法**
- `speaker: "interviewer" | "respondent" | "observer"` 写成裸字符串并散落在多处
- `status === "done"`、`status === "finished"`、`status === "completed"` 三种写法同时存在
- 评分维度名在 prompt 里一套、代码里另一套

**本项目落点**：说话人、访谈状态、五项评分维度都必须是枚举，且只在一处定义，其他地方引用它。

---

## 3. 缺值和零值分开

**无法判断不是 0 分**。缺数据必须能表达成「没有值」并附带说明缺什么。

**要拦的写法**
- 缺数据时给 0、给 3、给平均分
- 用 `""` 或 `-1` 表示缺失
- `score: null` 但没有任何字段说明为什么 null

**本项目落点**：观察者五项评分里，没有时间戳或话轮重叠标记时，「不打断」这一项必须是 `score: null` + `note: "缺少时间戳，无法判断是否打断"`。加权平均计算时必须排除 null 项，不能当 0 参与。

---

## 4. 纯计算与外部调用分开

大模型调用、文件读写、网络请求放在明确的边界；业务判断留在纯函数里。

**要拦的写法**
- 打分函数内部直接 `await fetch(model)`
- 解析逻辑和写文件写在同一个函数里
- 单位换算、加权求和这类计算依赖读环境变量

**为什么**：纯函数可复现（第 2 讲要求），外部调用不可复现。混在一起，测试就只能测到「跑通了」，测不到「算对了」。

**本项目落点**：`transcript -> 结构化数据`、`结构化数据 -> 加权分` 都该是纯函数，能拿样例文件直接跑；模型调用只负责产出结构化数据，不负责算分。

---

## 5. 更新产生新值，不覆盖旧值

访谈记录的每次变更要留痕，能回答「上一版长什么样」。

**要拦的写法**
- 直接改对象字段，不保留旧值
- 落盘时覆盖同名文件，没有版本或时间戳
- 一轮访谈进行中状态被就地修改，失败后无法回滚

**本项目落点**：写 `apps/workbench/records/` 用原子写入（临时文件 + rename），文件名带时间戳与访谈 ID。一轮的变更记成新的一条 round，不改旧的。

---

## 6. 模块先定接口再实现

跨模块的东西，先写清楚输入、输出、错误处理，再写实现。

**要拦的写法**
- 先写一个能跑的函数，接口靠调用方猜
- 错误用 `throw new Error("failed")` 一句话带过，调用方无法区分「网络失败」和「数据不合法」
- 输入输出结构只存在于 prompt 文字里，没有类型或 schema

**本项目落点**：工作台预留的 `next / respond / analyze` 三个接口，输入输出结构必须先定成 schema（或类型），再写适配层。现在只有名字、没有契约，这是当前最大的架构缺口。

---

## 7. 局部通过不等于整体通过

三个 Agent 各自测试通过，还要做一次组合层面的检查。

**要拦的写法**
- 「我这边跑通了」就当作集成完成
- 每个服务单独 mock 全绿，联调时字段名对不上
- 只验证了正常路径，没验证「一轮访谈中途断掉」

**本项目落点**：每次改完，除了各自 `pnpm dsh --profile headless "..."` 跑通，还要确认三边的字段名、枚举值、时间戳格式完全一致。

---

## 8. 加 Agent 之前先确认接口和验收条件

只加数量而接口含糊，集成时间会增加。**过细的拆分同样增加接口与协调成本**（课件原话）。

**要拦的写法**
- 「再加一个 Agent 负责 XX」但说不出它的输入是什么、输出给谁
- 新服务的验收条件写成「效果更好」
- 三个服务职责有重叠，同一件事两边都在做

**本项目落点**：采访者、受访者、观察者的边界已在 `Service_agents/*/README.md` 写清（采访者不读人物卡、受访者不配合诱导式提问、观察者只评采访者）。加第四个角色前，先把这四条边界重新核一遍。

---

## 三条一票否决

出现以下任一情况，直接打回，不进入细节讨论：

1. 改了上游 core（`Service_agents/*/packages/` 下非 `bundle` 的实现），没有事先报备。
2. `.env`、密钥、真实访谈原文被提交进仓库。
3. 评分逻辑里出现「缺数据就给中间分」。
